# Pawgress 開発の進め方

この文書は、Pawgress がどのような経緯で企画され、どのような手順で開発されたかをまとめたものです。何を作るかは `docs/product-spec.md` と `docs/ux-spec.md`、実装の構成は `docs/architecture.md` を参照してください。ここではそれらに至るまでの経緯と進め方を書きます。

## 1. 原点：タスク管理が苦手だったこと

Pawgress の出発点は、開発者自身が日常的なタスク管理を苦手としている経験です。普段からスケジュールや TODO の管理をあまり行わず、TODO を登録する行為そのものを面倒に感じ、タスクを登録したことで満足してしまって実行につながらないことがよくありました。仕事のチケット管理にも同じような苦手意識がありました。

この経験から、既存の TODO アプリに対してある問題意識を持つようになりました。「タスクを整理・管理できること」と「実際にタスクに取り組めること」は、必ずしも同じではないのではないか、という疑問です。TODO アプリがどれだけ高機能であっても、そのアプリを使うこと自体が負担になってしまえば、継続的な利用は難しくなります。

そこで、タスク管理が得意な人の生産性をさらに高めることよりも、「タスク管理が苦手な人でも、自然に使い続けられる TODO アプリを作れないか」という問いを企画の出発点としました。

## 2. 着想：Pokémon Sleep の日次・週次サイクル

企画初期に参考にしたサービスの一つが『Pokémon Sleep』です。特に注目したのは、日々の睡眠記録を通じてポケモンと出会い、一週間かけてカビゴンを育て、週の終わりに育成サイクルが切り替わり、翌週には新しい目標に取り組むという、日次・週次で区切られた体験設計でした。

ここで得たのは、Pokémon Sleep のゲームシステムそのものではありません。日々の行動を一定のサイクルの中に位置づけるという考え方を、着想として得ました。単発の行動を記録するだけでなく、一日という区切りを設けることで、行動の始まりと終わりが明確になります。この着想は、「今日取り組むことを決める → 一日の中で取り組む → 一日を振り返る → 翌日に新しいサイクルを始める」という日次ループ（`docs/product-spec.md` §2）につながっています。

## 3. 着想：スマートウォッチの小さな達成体験

もう一つの着想は、スマートウォッチなどの活動目標通知です。一日の歩数目標や週間の活動量目標を達成すると、小さな通知やアニメーションで知らされます。そこに大きな報酬があるわけではありませんが、達成を視覚的に確認できると少しうれしく感じられます。

この、日常の小さな行動にささやかな喜びを返す仕組みを TODO アプリにも取り入れたいと考え、Pawgress では相棒のリアクションやマイクロインタラクション（`docs/product-spec.md` §3 相棒）に反映しています。ただし演出そのものを目的にはせず、ユーザーの行動に対して意味のあるフィードバックを返すことを重視しています。

## 4. 模索と変更：ゲーム的な動機づけをめぐる試行錯誤

企画初期には、より強いゲーム性を持つ仕組みも検討していました。「一定期間内に TODO を達成することで、何かを守ったり救出したりする」というアイデアです。タスクの完了に、ゲーム内での明確な意味を与え、その行動がゲーム内の出来事につながることで取り組む動機を作れないか、という試みでした。

検討を進める中で、ペナルティや危機感を強調する仕組みが、タスク管理が苦手なユーザーに本当に適しているのか、という疑問が浮かび上がりました。未完了を期限切れの失敗として扱うことは、もともとタスク管理を苦手に感じている人にとって、むしろ使い続ける負担を増やしかねません。

そのため、最終的には未完了を責めたり失敗にペナルティを与えたりするのではなく、日々の小さな前進を肯定的に扱う方向へ整理しました。現在の「成功/失敗の判定ではない」という Review の設計（`docs/ux-spec.md` §4）や、連続達成記録・ランキングを実装しないという方針（`docs/product-spec.md` §4）は、この試行錯誤を経て定まったものです。初期から現在の設計がそのまま完成していたわけではありません。ゲーム的な動機づけを模索する過程で、プロダクトの目的との整合性を考えながら方針を変化させてきました。

## 5. 問題意識：キャラクターの魅力だけに依存しない

Pokémon Sleep を参考にする中で、もう一つの問題意識が生まれました。Pokémon Sleep が継続的に利用される背景には、ポケモンという強力なコンテンツの魅力があるのではないか、という見方です。キャラクターが魅力的であることと、アプリの体験そのものが優れていることは、必ずしも同じではありません。

Pawgress でも犬・猫の相棒を採用していますが、キャラクターがかわいいという理由だけで使い続けてもらうことを目指しているわけではありません。むしろ、キャラクターがいなくても使うこと自体に価値がある TODO アプリであることを重視しています。キャラクターは、タスクを選び、取り組み、振り返るという体験そのものの価値を補強する存在として位置づけており、会話やタスクの判断は行いません（`docs/ux-spec.md` §6）。

## 6. 体験の原型：朝の計画と夜の振り返り

企画段階で開発者自身が考えていた具体的な利用イメージは、「思いついたときにタスクを登録しておき、毎朝いくつかの TODO を決め、寝る前に完了・未完了を確認する」というものでした。このアイデアが、現在の Pawgress の基本的な体験構造に直接つながっています。

- 朝（Today Setup）: Inbox に蓄積したタスクから、今日取り組むものを少数に絞って選びます。
- 日中（Today Active）: 朝に決めたタスクに取り組み、進捗や完了に応じて相棒が小さなリアクションを返します。
- 夜（Review）: 一日の終わりに完了・未完了のタスクを確認し、未完了のものは翌日へ持ち越すか Inbox へ戻すかを判断します。

この一連の体験は、行動科学の理論を起点として考案したものではありません。まず開発者自身の生活上の課題と理想的な利用イメージがあり、その後、習慣形成や行動変容に関する研究を調査して、設計の妥当性や改善点を検討してきました。

## 7. 目指した体験：道具として使いやすく、少し楽しい

企画初期から、子どもでも直感的に理解でき、少しワクワクするような TODO アプリを目指していました。ただし、子ども向けのゲームを作ることが目的ではありません。TODO の登録・一覧表示・完了・編集削除といった基本的な操作は、一般的な TODO アプリの構造を尊重しています。そのうえで、相棒の小さなリアクションや完了時のフィードバック、朝と夜の体験の切り替え、日々の進捗の視覚的な表現といった部分に遊び心を加えています。

目指したのは、ゲームのような派手な演出ではなく、「道具としては使いやすく、触ってみると少し楽しい」という体験です。この考え方は、のちに採用した「Soft tactile editorial UI」という視覚方向性にもつながっています。

## 8. 仕様を先に固める

ここまでの背景（§1〜§7）を踏まえ、最初に取り組んだのは、プロダクトとしての輪郭を文章に書き出すことでした。日次ループと、意図的に実装しない機能を `docs/product-spec.md` として先に言語化し、何を作らないかを早い段階で決めたことで、後の実装判断に一貫した軸ができました。

情報設計（画面構成、ナビゲーション、各 interaction の不変条件）はプロダクト仕様とは別の文書（`docs/ux-spec.md`）に分けています。「何をするプロダクトか」と「それをどう画面に落とすか」は別の関心事であり、両者を混ぜると変更のたびにどちらの文書を直すべきか曖昧になるためです。

## 9. デザインリサーチと参考資料

UI の視覚的な設計を検討する際には、既存プロダクトのデザインや公開されている設計資料を積極的に参考にしました。

TODO・タスク管理アプリのUIパターン、画面レイアウトと情報階層、ナビゲーションやコンポーネントの構成、余白・タイポグラフィ・視覚的な強弱、直感的に操作できるUIの表現方法を調査する目的で、UI/UXデザインのリファレンスサービス [Refero](https://refero.design/) を利用しました。特定の画面をそのまま複製することは目的とせず、複数のプロダクトを比較しながら、Pawgress の設計コンセプトに適した表現を検討するための材料として扱っています。

デザイン仕様を言語化・構造化する方法、デザイントークンの定義方法、日本語タイポグラフィ（フォント・行間・字間）の考え方、AIエージェントにデザイン方針を伝達する方法を検討する目的で、実在する複数サービスの DESIGN.md を収集した [kzhrknt/awesome-design-md-jp](https://github.com/kzhrknt/awesome-design-md-jp) を参考にしました。note・MUJI・中川政七商店・Mercari・suzuri など各社の DESIGN.md に見られる色の役割分離や、色の使用量を絞るという設計思想を参考にしましたが、各社固有の色の数値やコンポーネント実装はそのまま複製していません。

Pawgress の企画・課題設定は、開発者自身の原体験（§1〜§7）から始まりました。その上で、実際のUIを設計する段階では、既存の優れたデザインや公開されている設計資料を材料として参考にしています。参考にしたのは個々のデザインが持つ設計思想であり、具体的な数値やレイアウトは Pawgress 固有の要件に合わせて都度検討し直しました。

## 10. Visual design system を先に作り、1画面で検証する

色・余白・文字サイズ・角丸・影といった視覚トークンは、先に token として定義してから画面実装に入りました。画面を作りながら都度決めると、画面ごとに値がばらつきやすいためです。

ただし token を先に全部決め切ろうとはしませんでした。最初に「Today（進行中）」画面 1 つを design-system の検証用画面として実装し、タイポグラフィの階層・余白のリズム・タスクの密度・色の役割・focus 状態などをそこで確定させてから、他の画面へ展開しました。1 画面で得られた知見（例えば「カードを多用しない」「色だけで状態を伝えない」）を以降の画面にも一貫して適用しています。

## 11. 画面は段階的に実装する

一度に全画面を作らず、ユーザーが実際にたどる順番で実装を進めました。

1. Today（Setup → Active → 完了後）
2. 今日を振り返る（Review）
3. Inbox
4. 記録（History）
5. 設定（Settings）

後続の画面を作る中で、先に作った画面と共通する構造（例えば「相棒を中心に据えた画面の外枠」）が見つかった場合は、都度まとめて共通化しました。重複が実際に発生してから抽出する、という順序を意識しています。最初から汎用化を狙うと、結局使われない抽象化を作り込んでしまうことがあるためです。

## 12. 実装のたびに視覚的な検証を行う

機能を実装するごとに、実際の画面で以下を確認しました。

- 320px / 390px / 768px / 1440px の各幅での表示崩れ
- キーボードのみでの操作と、フォーカスの可視性
- 200% ズーム時のレイアウト
- 長い日本語タイトルでの折り返し
- `prefers-reduced-motion` を尊重したアニメーションの無効化
- 空状態・完了状態など、タスクが 0 件のときと多いときの両方

アクセシビリティは Storybook の a11y addon と axe-core による自動検証に加え、実際にキーボードとスクリーンリーダーで操作して確認しています。

## 13. 実装完了後に体系的なコードレビューを行う

主要画面の実装が一通り終わった段階で、レイヤーごとに全体を見直すコードレビューを行いました。

```text
ドメイン層（純粋なビジネスロジック）
→ 永続化層
→ 共有UIコンポーネント・hooks
→ アプリの外枠（router / layout）
→ Companion
→ 各画面（Today → Review → Inbox → History → Settings）
```

下位レイヤーから見ていく順にしたのは、上位の画面が依存する前提を先に理解してから画面固有の実装を評価するためです。このレビューで見つかった問題（アクセシビリティ上の懸念、コードの重複、不自然な日本語表現、パフォーマンス上の無駄など）はその場で修正し、変更のたびに lint・型チェック・テスト・ビルドを通してから確定させています。

## 14. 開発ツール

実装には AI pair-programming ツール（Claude Code）を併用しました。仕様・設計判断は都度人が確認し、実装・リファクタリング・テストの実行とレビューはツールと協働して進めています。

## 15. 品質ゲート

すべての変更は、次が通ることを最低条件としています。

```text
npm run lint
npm run typecheck
npm test
npm run build
npm run build-storybook
```

詳細な品質目標は `docs/quality-targets.md` を参照してください。
